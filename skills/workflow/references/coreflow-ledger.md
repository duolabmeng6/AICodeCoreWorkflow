## 定位

把 CoreFlow Ledger 用作已授权需求、实施计划、关键决策和最终结果的项目内持久记录。把运行环境的任务计划工具用作实时进度视图；不要让留档文件替代实时执行列表。

CoreFlow Ledger 的全部生命周期操作禁止调用任何 Git 命令。不要使用 Git 判断项目根目录、检查文件、移动目录、暂存、提交或推送留档内容。开发任务本身是否使用 Git，由用户要求和上层指令另行决定。

## 根目录与命名

- 从当前工作区和实际修改范围判断项目根目录；不要调用 Git。多个项目根都可能成立且选择会改变留档位置时，先询问用户。
- 使用项目根目录下的隐藏目录 `./.coreflow/`，不要改成非隐藏目录或用户主目录。
- 使用 `{YYYY-MM-DD}-{中文任务概览}` 作为新任务 ID 和目录名，并让 `task.json.id` 与目录名完全一致。中文概览通常控制在 6–20 个中文字符，优先采用“对象 + 目标或动作”，使目录无需打开文件即可理解任务内容；不要机械复制冗长的用户原句。
- 中文概览的主体必须使用中文，可以保留 `API`、`Docker`、`Vue` 等必要技术名。移除空格、斜杠、反斜杠、冒号、引号及其他文件系统特殊字符，不使用纯英文 slug。
- 同日同名目录已存在时，先判断是否为当前任务的续作；是则恢复，不能确定则询问。新任务冲突时追加递增后缀，如 `-2`，不要覆盖。
- 已有英文任务目录属于有效历史记录，可以继续恢复、完成和归档；不要仅为符合新命名规则而批量迁移或改名。

```text
./.coreflow/
└── tasks/
    ├── {YYYY-MM-DD-中文任务概览}/
    │   ├── task.json
    │   ├── prd.md
    │   ├── implement.md
    │   ├── design.md       # 按需
    │   ├── review.md       # 评审时创建
    │   └── research/       # 按需
    └── archive/
        └── {YYYY-MM}/
            └── {YYYY-MM-DD-中文任务概览}/
```

## 工件职责

| 工件 | 创建时机 | 内容 |
| --- | --- | --- |
| `task.json` | 实施授权后 | 机器可读元信息、状态、时间和工件索引 |
| `prd.md` | 实施授权后 | 目标、范围、非目标、约束、假设和验收标准 |
| `implement.md` | 实施授权后 | 已授权实施步骤、预期结果、验证方式和计划修订 |
| `design.md` | 复杂任务按需 | 架构边界、接口、数据流、取舍、兼容和回滚 |
| `research/` | 有持久价值时 | 按主题保存事实、来源、结论及其对决策的影响 |
| `review.md` | 评审阶段 | 实际改动、验证结果、计划偏离、未验证项和残余风险 |

不要默认创建 `implement.jsonl`、`check.jsonl`、事件日志、会话指针或代理运行轨迹。只有用户明确要求扩展格式时才增加额外工件。

## 状态

| 状态 | 使用条件 |
| --- | --- |
| `in_progress` | 实施已授权，任务正在实施或等待正常推进 |
| `blocked` | 存在真实阻塞，无法在当前权限和上下文内继续 |
| `completed` | 已达到完成标准并完成评审，等待用户决定是否归档 |
| `archived` | 用户已明确确认归档，任务目录已移入归档区 |

不要提前标记 `completed` 或 `archived`。阻塞解除后把状态恢复为 `in_progress`；同步更新 `updatedAt`。

## `task.json`

使用有效 JSON，不写注释。时间使用包含时区的 ISO 8601 格式；尚未发生的时间使用 `null`。

```json
{
  "schema": "coreflow-ledger/v1",
  "id": "2026-07-19-实现示例功能",
  "title": "示例任务",
  "status": "in_progress",
  "complexity": "standard",
  "createdAt": "2026-07-19T10:00:00+08:00",
  "approvedAt": "2026-07-19T10:00:00+08:00",
  "updatedAt": "2026-07-19T10:00:00+08:00",
  "completedAt": null,
  "archivedAt": null,
  "summary": "实现并验证已授权的任务目标。",
  "artifacts": {
    "prd": "prd.md",
    "implement": "implement.md",
    "design": null,
    "review": null,
    "research": []
  }
}
```

使用 `simple`、`standard` 或 `complex` 表示 `complexity`。`approvedAt` 保留为兼容字段，用于记录实施授权生效时间：普通实现请求取计划完成并开始自动执行的时间，讨论优先模式取用户明确批准计划的时间。工件创建或移除时同步更新 `artifacts`；不要记录绝对个人路径、模型名称、令牌用量或无助于恢复任务的运行细节。

## 文档内容

### `prd.md`

依次记录：任务标题、背景与目标、范围、非目标、约束与假设、验收标准。把用户明确表达或讨论中最终确认的解释作为准确信息，不保留已被替代的候选需求。

### `implement.md`

依次记录：实施授权时间、授权方式、复杂度分类及理由、影响区域、编排计划、所有权/依赖/验证、实施步骤、每步预期结果和验证方式、风险与回滚。记录屏障、失败/回退及计划修订。不得记录代理身份、模型、令牌、完整提示、transcript、原始日志或实时状态。

### `design.md`

只在接口、数据模型、跨模块交互、兼容策略、安全边界或回滚设计需要长期保存时创建。记录结论、证据和取舍，不展开模型隐式推理。

### `research/`

每个主题使用一个简短 Markdown 文件，记录问题、来源、已验证事实、结论、证据位置和未决项及其对当前任务的影响。不要保存代理身份、密钥、凭据、敏感数据、大段原始日志或思维链。

### `review.md`

依次记录：评审结论、实际完成内容、验证命令与结果、发现（严重性/证据/负责人/处置/验证及复评）、计划偏离、未验证项、残余风险和归档决定。只记录真实执行过的验证，不把未运行检查写成通过。

## 生命周期

### 创建或恢复

1. 判断实施授权方式：普通实现请求在计划完成后自动获得范围内实施授权；用户主要要求讨论、评审或确认方案与计划，或明确要求实施前等待时，必须先获得明确批准。
2. 实施获得授权后，若环境提供任务计划工具，先同步实际实施与验证步骤。
3. 读取本规范并定位项目根目录，不运行 Git 命令。
4. 检查 `./.coreflow/tasks/` 是否已有同一任务的活跃记录；恢复续作，避免重复创建。
5. 新建任务时写入 `task.json`、`prd.md` 和 `implement.md`，状态设为 `in_progress`。
6. 只在确有需要时创建 `design.md` 和 `research/`。

### 执行与修订

- 使用环境任务计划工具维护实时进度；只在重要状态、已授权计划、持久决策或验证结果变化时更新 CoreFlow Ledger。
- 出现真实阻塞时把状态改为 `blocked` 并记录继续推进所需条件；解除后恢复为 `in_progress`。
- 计划在原授权边界内变化时追加 `implement.md` 修订、同步相关工件并继续执行；需要改变目标、扩大范围、改变外部行为或取得新权限时先返回计划阶段，用户确认后再记录和实施。

### 评审与归档

1. 在评审阶段创建或更新 `review.md`。
2. 未达到完成标准时保持 `in_progress` 或 `blocked`，不要询问归档。
3. 达到完成标准时把状态改为 `completed`，写入 `completedAt` 和 `updatedAt`，然后明确询问：`任务已完成并通过评审，是否归档至 ./.coreflow/tasks/archive/{YYYY-MM}/{task-id}/？`
4. 用户暂不归档时保留活跃目录和 `completed` 状态，在最终结果中给出待归档路径。
5. 用户确认归档时，先确认目标目录不存在；仅使用普通文件系统操作移动整个任务目录，不使用 `git mv` 或其他 Git 命令。
6. 移动成功后，在归档目录内把状态更新为 `archived`，写入 `archivedAt` 和 `updatedAt`，并在 `review.md` 记录归档决定。
7. 目标冲突、移动失败或状态更新失败时不要覆盖或删除任何记录；报告当前源路径、目标路径和继续处理所需条件。

## Git 禁令

CoreFlow Ledger 的创建、读取、更新、验证和归档过程中不得运行任何 Git 命令，包括但不限于 `git status`、`git diff`、`git mv`、`git add`、`git commit` 和 `git push`。不得自动更改忽略规则、暂存区、提交历史、分支或远端状态。
