## Agent 编排

- 只有根代理负责需求澄清、规划、架构、任务分解、集成与最终验收。
- 自定义代理是可用的工具箱，不是固定团队。不要仅仅因为角色存在就生成代理。
- 在根线程中直接处理琐碎或单步任务。
- 生成代理时选择实际的自定义角色（在相应界面支持的情况下使用 `agent_type`）。角色化的任务名称只是标签，不能替代对角色的选择。
- 如果请求的自定义角色不可用，不要静默改用通用代理；应在根线程中处理任务，或报告该限制。

### 路由

- 对不熟悉的代码库、执行路径追踪、依赖关系梳理、大文件扫描和证据收集，使用 `terra-explorer`。
- 只有在范围、文件所有权、验收标准和验证步骤明确后，才使用 `luna-worker`。
- 当独立评审能显著降低风险时，尤其是涉及非平凡逻辑、多文件变更、用户可见行为或测试覆盖不完整时，实施后使用 `terra-reviewer`。
- 对琐碎、完全机械化且已完成客观验证的变更，跳过单独的评审者。
- 架构、安全敏感决策、数据迁移、歧义需求、跨系统集成和复杂调试应由根代理处理。
- 对需要更深入单代理推理的困难工作，使用 Sol Max。
- 只有在任务可拆分为有意义的独立工作流，且并行处理能显著提升速度或质量时，才使用 Sol Ultra。

### 工作流

- 对不熟悉的实施工作：先探索，再规划、实施、评审，最后集成。
- 不得让 reviewer 与其所评审的 worker 并发运行；必须等 worker 完成后再开始评审。
- 对 PR 评审或调查，可按独立评审维度并行运行多个只读代理。
- 对代码变更，默认使用一个可写代理。
- 只有在根代理分配了明确且互不重叠的文件所有权时，才允许多个写入者并行工作。
- 将自定义代理的 `sandbox_mode = "read-only"` 视为纵深防御的默认设置；若父级轮次已经具有实时写权限，它并不是可保证的隔离边界，父级运行时策略可能重新应用到子代理。
- 在可写的父级轮次中，明确告知探索者和评审者不要修改文件；在生成它们之前建立相关工作树基线，并在之后验证它们没有产生更改。
- 当需要严格的只读隔离时，应在委派前以 Read Only 模式启动单独的根任务，而不是将审计混入可写的实施任务。

### 验证

- 将子代理结果视为证据，而不是最终事实。
- 子代理必须返回提炼后的摘要，而不是原始日志或宽泛的搜索输出。
- 根代理必须检查最终 diff 和已修改文件。
- 根代理必须在报告完成前运行适当的集成测试、类型检查、lint 检查或构建检查。
- 明确报告无法运行的测试以及所有剩余风险。
- 子代理不得进一步委派。
